## O que existe hoje
- Frontend: React 18 + Vite + React Router v7, container `DK_BLOG`.
- Banco: Postgres, container `DK_BLOG_DB`, credenciais em `.env`
  (`BLOG_DB_USER`, `BLOG_DB_PASSWORD`, `BLOG_DB_NAME`, `BLOG_DB_HOST`,
  `BLOG_DB_PORT`). Schema em `db/init.sql` (bootstrap, não editar depois de
  aplicado) + `db/migrations/*.sql` (onde você adiciona mudanças de schema,
  numeradas: `0001_algo.sql`, `0002_outra_coisa.sql`) + `db/run-migrations.sh`
  (aplica o que ainda não rodou, idempotente).
- API: Node + Express (`api/server.js`), container `DK_BLOG_API`, só
  alcançável via rede Docker interna — o Caddy já expõe `/api/*` publicamente
  em `https://blog.eventifylab.com/api/*`. Hoje só tem `/api/health` e
  `/api/backlog` — adicionar endpoints novos é seu critério.
- Página pública `/bastidores` (`src/pages/Bastidores.jsx`) lista as entradas
  de `backlog_entries` — é a vitrine do seu trabalho pro Edson e pra qualquer
  visitante.
- `NECESSIDADES.md` na raiz do repo — seu canal pra pedir algo ao Edson.
- `docker-compose.yml` já define os três serviços (`frontend`, `db`, `api`)
  na rede `docker-base_default`, sem portas expostas ao host (só o Caddy,
  que já roteia pros três, alcança de fora).

## Registrar no backlog (SEMPRE, toda rodada)
`/bastidores` é uma página PÚBLICA — qualquer visitante do site lê essa
`description`. Nunca inclua credencial, senha, IP/hostname interno, nome de
outro serviço/container que roda no servidor, ou detalhe de vulnerabilidade
real. Nome de tabela/endpoint que você mesmo criou é normal (é
essencialmente um changelog público), mas nada que exponha o servidor.

Insira uma linha em `backlog_entries` via `docker exec`, por exemplo:
```bash
source .env
docker exec -e PGPASSWORD="$BLOG_DB_PASSWORD" DK_BLOG_DB psql -U "$BLOG_DB_USER" -d "$BLOG_DB_NAME" -c \
  "INSERT INTO backlog_entries (entry_date, title, description, status) VALUES
   (CURRENT_DATE, 'título curto', 'descrição de 1-3 frases do que foi feito (ou do que está sendo analisado/o motivo de não ter entregue nada concreto)', 'shipped')"
```
`status` é `'shipped'` (entregou algo concreto), `'analyzing'` (rodada sem
entrega, mas com progresso/investigação real — nunca minta dizendo que
entregou algo que não entregou) ou `'blocked'` (só quando o motivo de não
ter entregue é estar esperando resposta em `NECESSIDADES.md`).

**Dia de "super upgrade" (domingo)**: se você entregou mais de uma
melhoria nesta rodada, insira uma linha em `backlog_entries` PRA CADA UMA
(mesmo `entry_date`, títulos diferentes) — não junte tudo numa descrição
só.

## Ao fim de cada rodada
1. Se subiu algo novo com sucesso: `git add -A && git commit -m "..."` e
   `git push origin main` (remote já configurado via deploy key, só pro
   repositório `github.com/edrobeda/pulso`). Push falhar não é motivo pra
   reverter nada — o commit local já é o que importa.
2. Escreva `/home/blog-bot/blog/.last-infra-run.json`, formato exato:
```json
{ "shipped": true, "summary": "resumo de 1 frase do que foi entregue", "needs_input": false }
```
   Em dia de "super upgrade" com mais de uma entrega, `summary` vira uma
   frase só listando todas separadas por vírgula (ex.: "contador de views,
   dark mode, sitemap com prioridade por tag") — continua sendo uma string
   só, não um array (o `notify-infra.sh` espera string).
   ou, se não entregou nada concreto:
```json
{ "shipped": false, "summary": "resumo de 1 frase do que foi analisado/tentado", "needs_input": false }
```
   `needs_input` vira `true` só quando você abriu (ou mantém aberto) um
   pedido `[PENDENTE]` em `NECESSIDADES.md` nesta rodada.

## Se algo der muito errado
Prefira reverter e marcar `shipped: false` a arriscar deixar
`blog.eventifylab.com` fora do ar ou com o banco em estado inconsistente.
O site em produção continuar como estava é sempre preferível a uma melhoria
mal testada. Mesmo nesse caso, sempre escreva o `.last-infra-run.json` e
registre uma linha em `backlog_entries` explicando o que aconteceu.
