## O kit iaBrain e seu manifesto versionado
`public/downloads/iabrain/` guarda um kit especial versionado (não é uma
lição isolada como as outras): `latest.json` (aponta pra versão mais
recente), `CHANGELOG.md` (histórico entre versões), `install-prompt.md`
(prompt que o usuário final cola no próprio agente dele pra instalar ou
atualizar automaticamente — lê `latest.json` primeiro) e uma pasta por
versão (`v0.01/`, `v0.02/`...) com um `manifest.json` próprio listando
todo o conteúdo daquela versão.

**Se você decidir evoluir o iaBrain nesta rodada** (adicionar um arquivo
novo ao padrão, corrigir algo relevante em mais de um arquivo, mudar a
estrutura): SEMPRE crie uma pasta de versão NOVA (`v0.02/` etc, nunca
edite uma pasta de versão já publicada) e:
1. Copie os arquivos da versão anterior que não mudaram + adicione/edite
   os que mudaram na pasta nova.
2. Escreva um `manifest.json` novo pra essa versão (mesmo formato do
   `v0.01/manifest.json` — `version`, `disclaimer`, `base_url`, `files[]`
   com `file`/`role`/`description`/`suggested_target` quando aplicável).
3. Atualize `latest.json` na raiz de `iabrain/` (`latest_version` e
   `manifest_url` apontando pra nova pasta).
4. Adicione uma entrada nova no topo de `CHANGELOG.md` (formato: `##
   v0.0X — AAAA-MM-DD` + 1-3 frases do que mudou e por quê).
5. Atualize a lição do iaBrain em `src/content/lab/lessons.js` (a
   `lesson` já cita a versão atual — mantenha coerente) e a lista
   `downloads` se algum arquivo novo precisa aparecer na página.
`install-prompt.md` não muda entre versões normalmente (ele é
version-agnostic por design, lê tudo via `latest.json`/`manifest.json`) —
só edite se o próprio processo de instalação precisar mudar.

## O que fazer nesta rodada
1. Leia `src/content/lab/lessons.js` inteiro (não é grande, essa é a
   exceção) pra saber o que já existe e não repetir.
2. Releia `NECESSIDADES.md` inteiro — se alguma entrada `[PENDENTE]` sua
   tiver sido respondida, trate como os outros agentes (credencial vai pro
   `.env`, decisão vira ação, sem duplicar pedido).
3. Procure uma lição nova candidata, nesta ordem de preferência:
   a. As últimas ~20 linhas de `CHANGELOG.md` (do agente de publicação) e
      as últimas 5 linhas de `.agent-logs/runs.log` — algum bug real,
      correção ou decisão de arquitetura recente que valha virar lição
      genérica (sem nomes de domínio, credencial ou detalhe específico
      deste servidor)?
   b. As últimas 5 entradas de `backlog_entries` (via `docker exec` +
      `psql`, `ORDER BY entry_date DESC, id DESC LIMIT 5`) — alguma
      melhoria do diretor de infra virou um aprendizado reaproveitável?
   c. Se nada novo e genuíno surgiu, é normal não adicionar nada nesta
      rodada — não invente uma lição fraca só pra preencher.
4. Se encontrou uma lição nova de verdade:
   - Adicione um item em `lessons.js` (problema real, genericizado, sem
     vazar nome de domínio/servidor/credencial) e o `download` correspondente
     em `public/downloads/` (com aviso legal no cabeçalho).
   - Ou, se a lição já existe mas o `download` pode melhorar (mais preciso,
     mais testável), edite o arquivo de download existente em vez de criar
     um novo — evite duplicar conteúdo quase igual.
5. Alternativamente (menos comum, mas válido): revisar e melhorar uma
   lição/download existente que esteja confuso, desatualizado ou incompleto.

## Testar antes de subir
1. `cd /home/blog-bot/blog && npm install` só se `package.json` mudou

   Se falhar e você não conseguir corrigir, reverta (`git checkout -- .` nos
   arquivos alterados, `docker compose up -d frontend` de novo) e marque a
   rodada como não entregue — nunca deixe a página quebrada no ar.

## Registrar no backlog (SEMPRE, toda rodada com entrega)
`/bastidores` é pública. Nunca inclua credencial, IP/hostname interno ou
nome de outro serviço do servidor na `description`.

```bash
source .env
docker exec -e PGPASSWORD="$BLOG_DB_PASSWORD" DK_BLOG_DB psql -U "$BLOG_DB_USER" -d "$BLOG_DB_NAME" -c \
  "INSERT INTO backlog_entries (entry_date, title, description, status) VALUES
   (CURRENT_DATE, 'título curto', 'descrição de 1-3 frases da lição adicionada/revisada, ou do que foi analisado sem entrega', 'shipped')"
```
`status`: `'shipped'` (entregou lição/download novo ou revisão real),
`'analyzing'` (rodada sem entrega, mas com verificação real de que nada
novo surgiu — nunca minta dizendo que entregou), `'blocked'` (só esperando
resposta em `NECESSIDADES.md`).

## Ao fim de cada rodada
1. Se subiu algo novo: `git add -A && git commit -m "..."` (sem `git push`
   — o sync automático pro GitHub, se existir pra este projeto, é território
   de outro processo).
2. Escreva `/home/blog-bot/blog/.last-laboratorio-run.json`:
```json
{ "shipped": true, "summary": "resumo de 1 frase do que foi entregue", "needs_input": false }
```
   ou, sem entrega:
```json
{ "shipped": false, "summary": "resumo de 1 frase do que foi verificado", "needs_input": false }
```

## Se algo der muito errado
Prefira reverter e marcar `shipped: false` a arriscar deixar
`blog.eventifylab.com/laboratorio` quebrado no ar. Mesmo assim, sempre
escreva o `.last-laboratorio-run.json` e registre uma linha em
`backlog_entries`.
